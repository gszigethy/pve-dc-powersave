# Code review — October 2026 (v0.2.1-beta.1)

A full read of every file at `724d2b6` (2,592 lines), covering bugs, function and gaps, security, and performance. Fixes ship as separate, independently mergeable branches. This document is the index, and it records the analysis and proposals that are not implemented.

**How this was verified:** every fix has unit tests that fail on `main`, unless noted otherwise. All CI gates pass on each branch and on all branches merged together (141 tests, Perl statement coverage 93.7%, perlcritic, shellcheck, Python 3, `node --check`). **No live Proxmox node was available**, so the items marked ⚠️ need a check on a test node before release.

## 1. How the system works

```text
                        ┌──────────── every node ─────────────┐
 /etc/pve/dc-powersave.cfg ──► Controller.run (loop, 2 s)       │
   (pmxcfs, shared)           │  digest / reconcile.request /   │
                              │  EventObserver.fingerprint ──► wake?
                              ▼                                  │
                       Controller.reconcile (flock)               │
                         ├─ Config.load                          │
                         ├─ CpupowerBackend.discover (sysfs)     │
                         ├─ RuntimeStateCollector.collect ──► pvesh × (4+N)
                         ├─ [idle delay elapsed] collect again   │
                         ├─ DesiredState.decide (pure)           │
                         ├─ set_governor + verify (cpupower)     │
                         └─ /run/pve-dc-powersave/status.json ◄──┼── GET /nodes/{n}/power-management (pveproxy)
                                                                 │
 UI (ExtJS) ── GET/PUT /cluster/power-management ────────────────┼── PUT: pvedaemon → ClusterCapabilities → pvesh × (1+N)
            ── GET /cluster/power-management/capabilities ───────┘
```

- **Decision rule:** *active is the fallback, idle needs proof.* IDLE needs a complete guest view (`/nodes/<self>/qemu|lxc`), a complete task view (`/cluster/tasks` plus every online node's active tasks), quorum, valid CPU policies supporting the idle governor, no protection, no boot protection, `idle_candidate_delay` elapsed, and a second snapshot just before the change.
- **States:** `ACTIVE`, `IDLE_CANDIDATE` (empty, waiting), `IDLE`, `PROTECTED` (migration or lifecycle → `migration_governor`), `ERROR` (failsafe requested), `DISABLED`.
- **Migrations:** the PVE task list never contains a destination node, so in practice every migration or HA task protects **every** node until it ends.
- **Disabled mode is a dry run:** the controller still collects guest and task state, and the UI shows counts and protection. This is what the README's validation step relies on.
- **Process placement matters:** `pveproxy` (www-data) runs API methods without `protected`, `pvedaemon` (root) runs protected ones, and the controller runs as root under systemd. `pvesh` requires root and proxies remote-node paths over SSH.

### Suggested merge order

The branches are independent and merge cleanly in any order (checked forwards and backwards), with one exception: **`subprocess` is stacked on `offline-cpus`**. Suggested order, by value and risk:

1. `security`, 2. `capabilities-privilege` ⚠️, 3. `host-tasks`, 4. `offline-cpus`, 5. `subprocess`, 6. `controller`, 7. `ui`, 8. `perf` ⚠️, 9. `uninstall` ⚠️

`CHANGELOG.md` is deliberately not touched by any branch, so they do not conflict with each other. Each commit message is written to be copied into the changelog at release time.

## 3. Security review

**Threat model.** A root daemon on every node; API endpoints behind PVE authentication (`Sys.Audit` to read, `Sys.Modify` to write); an installer that edits core PVE files; a script injected into every PVE web page.

| Topic | Result |
| --- | --- |
| Command injection | **Clean.** Every `cpupower` and `pvesh` call uses list-form `open3` (no shell). Governor names are validated with `^[A-Za-z0-9_.-]+$` in config, API schema and backend. Node names are validated before they are interpolated into API paths. |
| Path and file handling | Config uses digest-checked atomic rename under `cfs_lock_file`. Status is written atomically into a root-owned directory. **The lock file was in a world-writable directory (finding 1, fixed).** |
| AuthZ | Reads need `Sys.Audit` on `/` or `/nodes/{node}`; policy writes and reconcile need `Sys.Modify`. No endpoint takes an arbitrary governor or command. PVE enforces CSRF for non-GET requests. Correct. |
| Privilege boundaries | The capabilities endpoint ran in the wrong daemon (finding 3, fixed). Once fixed, a `Sys.Audit` user can make the API node fan out `1+N` root `pvesh`/SSH processes per request. That is a low-risk amplification, but worth a cache (P-7 below). |
| XSS | All grid cells, notices and error dialogs are HTML-encoded. The detail dialog title was not; node names are constrained by PVE, so this was hardening only (fixed in `ui`). |
| Supply chain | Actions are pinned to SHAs; Dependabot is on; releases only come from tags on `main`. The installer defaults to the **moving `main` branch** over `curl \| bash`, and the published `SHA256SUMS` is not used by the installer (P-9). |
| Integration risk | The UI script overrides `PVE.panel.Config.initComponent` for every page, so a runtime error there can break the whole Datacenter view. The integration edits core PVE files; it has backups, `perl -c` checks and rollback. A `pve-manager` upgrade silently removes the registrations (P-2). |
| Process hardening | The unit runs as root with no sandboxing (P-10). |
| Information exposure | `last_error` can contain `pvesh`/SSH stderr (host names) and is visible to `Sys.Audit` users. Acceptable. |

## 4. Performance

Cost model per node with the defaults (2 s poll, 30 s reconcile), for N nodes. Every `pvesh` is a fresh Perl process loading the PVE API, and every remote-node `pvesh` path is an SSH session plus a `pvesh` on the remote node.

| Path | Before | After branches |
| --- | --- | --- |
| Wake-up hint | 1 `pvesh` / 2 s (always) | in-process IPC; `pvesh` only as fallback |
| Reconcile, non-idle | 4+N `pvesh` (N−1 over SSH), 3 `cpupower` | unchanged |
| Reconcile, steady IDLE | 2 × (4+N) `pvesh` | 4+N |
| UI open | (1+N) `pvesh` + (N−1) SSH every 15 s | on show and Refresh only |

Remaining proposals, highest gain first:

- **PERF-1:** In-process runtime collection. `/cluster/status` can come from `PVE::Cluster::get_members()` plus `check_cfs_quorum(1)`, guest state from `PVE::QemuServer::vmstatus()` / `PVE::LXC::vmstatus()`, and the cluster task list as in `perf`. This removes almost every `pvesh` spawn. The per-remote-node active-task queries over SSH are the hard part: the code says the cluster task list "lags", so this needs measuring on a cluster before it is replaced.
- **PERF-2:** Publish each node's capabilities and status through `PVE::Cluster::broadcast_node_kv('dc-powersave', …)`, and read them with `get_node_kv`. The capability endpoint then becomes one IPC call instead of an SSH fan-out, and node status works even when a node's API is unreachable.
- **PERF-3:** Cache `cpupower --version` per process (keyed on the binary's mtime). `discover` runs it 2–4 times per reconcile.
- **PERF-4:** Drop `--verbose` from the unit. `_log_change` already logs every state change; verbose adds about 2,900 identical lines per node per day.

## 5. Functional gaps and proposals

Ordered by value. *Design decision* means I recommend talking it through before implementing.

- **P-1 (design decision, safety): disable, stop or crash leaves the idle governor in place.** If a node is `IDLE` on generic `powersave` (minimum clock) when the policy is disabled, the service stops, or the controller crashes in a loop, guests started later run at minimum clock indefinitely. The README documents "Disabling leaves the current governor as is", but it is easy to miss. Options: (a) on a `managed → DISABLED` transition, apply `active_governor` once; (b) `ExecStopPost=` applies the failsafe governor; (c) at least list nodes still on the idle governor in the UI when saving a disabled policy. I recommend (a) plus (c).
- **P-2: survive `pve-manager` upgrades automatically.** Add `/etc/apt/apt.conf.d/99pve-dc-powersave` with `DPkg::Post-Invoke { "[ -x /usr/lib/pve-dc-powersave/integrate-pve.py ] && /usr/lib/pve-dc-powersave/integrate-pve.py || true"; };`. The helper is idempotent, refuses unknown layouts and rolls back; with the `uninstall` branch merged it also restarts the API daemons only when it changed a file. The uninstaller would remove the hook.
- **P-3: dry-run preview while disabled.** Publish `would_state` / `would_governor` by running `DesiredState->decide` with `enabled => 1`, and show it in the grid. The README's "watch the rows, then enable" step becomes concrete.
- **P-4: plugin version in status.** Add `plugin_version` to `status.json`. `ClusterCapabilities` would then refuse to enable on mixed versions and the UI would flag them. This matters because every node runs its own copy, and rolling upgrades are the norm.
- **P-5: per-node participation and overrides.** Excluding a node (for example a NAS-like node that must stay fast), and per-node governor mapping for mixed Intel/AMD clusters where no common governor exists.
- **P-6: EPP awareness.** On `intel_pstate` and `amd-pstate-epp` active mode, the governor choice is coarse (`performance` or `powersave`) and `energy_performance_preference` is the real knob. Optionally manage EPP alongside the governor.
- **P-7: cache capability discovery** in `/run` for about 10 s in `pvedaemon`, to cap the `Sys.Audit`-triggered fan-out (§3).
- **P-8: persist `managed`** in `/var/lib/pve-dc-powersave/` so a restart while pmxcfs is unavailable still knows it was managing. This is a known limitation from PR #4.
- **P-9: release-based installer.** `--version vX.Y.Z` downloads the release tarball and verifies it against `SHA256SUMS`. Make that the README default instead of `main`.
- **P-10: systemd hardening** after on-node testing: `NoNewPrivileges=yes`, `ProtectSystem=full`, `PrivateTmp=yes`, `ProtectKernelModules=yes`, `RestrictSUIDSGID=yes`. Keep `/sys` writable for cpufreq; `pvesh` needs `/var/log/pve`, `/etc/pve` and SSH.
- **P-11: use a dedicated cluster lock.** `PUT` borrows `cfs_lock_file('datacenter.cfg', …)`; `PVE::Cluster::cfs_lock_domain('dc-powersave', …)` avoids blocking unrelated `datacenter.cfg` edits.
- **P-12: policy edits while a node is offline.** With the policy enabled, any `PUT` (even an interval change) requires every node online and fresh. Only re-validate governors when they change, or when going from disabled to enabled.
- **P-13: stale threshold vs. slow reconciles.** One reconcile can take `(4+N) × 10 s` × 2 when `pvesh` times out. On larger or degraded clusters that exceeds the 120 s stale threshold and shows a running node as stale. Publish a "reconciling since" heartbeat, or scale the threshold.
- **P-14: notifications.** Send ERROR, stale nodes and policy changes through the PVE notification system (PVE 8.1+).
- **P-15: metrics.** Time spent in each state and the number of transitions per node, for judging whether the tool saves anything.
- **P-16: `cpupower` exit vs. readback.** On some hosts `cpupower -c all` exits non-zero while every online policy reads back correctly; that is treated as a failure today. Consider treating the readback as authoritative, or writing `scaling_governor` per policy directly (no `cpupower` dependency, per-policy errors).

## 6. Tests and quality gaps

- **JS:** no automated test. A small harness that stubs `Ext` and tests the data functions (`restoreGovernorFields`, the capability notice text, the stale-generation guard) would cover the logic without a browser.
- **`PVE::API2::Nodes::DCPowerSave`** (staleness math, reconcile request) and **`bin/`** have no tests. Making the `/run` paths injectable would allow both.
- **Coverage floors:** Python is at 84% after `uninstall`, against a floor of 45%. Perl would be at 93.7% with all branches merged, against a floor of 80%. Both floors can be raised.
- **CHANGELOG:** add an "Unreleased" section, so each PR can add a line without conflicting on the version header.
